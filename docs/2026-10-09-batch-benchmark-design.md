# Strata 批量 Benchmark 设计规格

日期：2026-10-09  
状态：待用户审阅  
实现方案：方案 A，启动器外层独立编排器

## 1. 目标

为当前 Windows Strata 启动器增加独立的批量 Benchmark 功能，在同一台电脑上对多个已安装模型进行可重复的性能、上下文、Agent 能力和稳定性比较，并生成可查看、可追溯的本地报告。

首批支持当前已安装的三个模型配置：

- `strata-iq3_s.json`
- `strata-unsloth-ud-iq4_xs.json`
- `strata-unsloth-ud-q4_k_xl.json`

工具只识别根目录中通过现有启动器校验、包含 `exe`、`args` 和 `model_name` 的 `strata-*.json`。以后经官方 setup 导入的新模型会自动出现在可选列表中。

## 2. 边界

### 2.1 官方文件只读

Benchmark 不修改以下官方内容：

- `src/`
- `include/`
- `serve/`
- `tools/`
- `bench/`
- `setup.py`
- `START-HERE.bat`
- `engine/strata.exe`
- 根目录现有 `strata-*.json`
- `%APPDATA%\Strata\settings.json`

测试需要改变端口、上下文、缓存或其他参数时，将原模型 JSON 复制到本次报告的 `configs/` 目录，只修改该临时副本。

### 2.2 自定义代码位置

新增代码和生成结果只放在 `launcher/`：

```text
launcher/
  benchmark/
    runner.py
    report.py
    agent_cases.json
  reports/
  docs/
    2026-10-09-batch-benchmark-design.md
```

现有 `launcher/Strata-Launcher.ps1` 只增加入口、参数收集、进度窗口和打开报告功能。测试编排、进程管理、数据采集和报告生成放在 Python 文件中，避免继续扩大 PowerShell 主文件的职责。

## 3. 公平比较原则

不同量化和模型包继续使用各自官方 setup 生成的引擎配置。工具不强制统一专家缓存、MTP 文件、模型路径等模型相关设置。

跨模型保持一致的条件包括：

- 相同测试 Prompt 和任务集
- 相同目标上下文长度
- 相同 API 采样参数
- 相同输出 token 上限
- 相同正式重复次数
- 相同缓存状态定义
- 相同测试阶段顺序
- 相同统计方法

报告保存每个模型的临时配置快照和配置摘要，明确列出模型之间实际存在的设置差异。

## 4. 用户界面

主启动器的“官方工具”附近增加“批量 Benchmark”按钮。按钮打开独立窗口，不把完整测试设置塞进当前主窗口。

独立窗口包含：

### 4.1 模型选择

- 列出所有有效的 `strata-*.json`
- 默认选中当前三个模型
- 显示 `model_name`、配置文件名和模型目录

### 4.2 测试预设

当前预设按测试问题拆分，均默认使用原生 256K 上限：

| 预设 | 输入与项目 | 轮数及并发 |
| --- | --- | --- |
| 日常速测 | 1K/4K 性能、4K 召回/并发、缓存、7 道 Agent 题 | 1 轮；并发 1/2 客户端各 1 组 |
| 日常完整 | 1K/4K/32K 性能、4K/32K 召回、4K 并发、缓存、9 道 Agent 题、短时稳定性 | 3 轮；并发 1/2 客户端各 3 组 |
| 长文对照 | 32K/128K 性能与召回 | 1 轮；无并发 |
| 并发专项 | 4K/32K 冷输入并发 | 1 轮；1/2 客户端各 2 组 |
| 容量极限 | 256K 性能与召回、接近上限的容量探测 | 1 轮；无并发 |

Agent 断言通过率只代表内置题集。稳定性测试发送 10 次短请求。界面切换预设时会填入对应的项目、输入长度和最大并发；之后可以手动调整。输入勾选与预设的召回/并发长度取交集，所选项目若没有可运行的长度则在模型启动前拒绝。取消全部模型上限时沿用源配置，并校验所选模型的上限一致且能容纳输入。手动设置“最大并发 4”会展开为 1、2、3、4 客户端测试。

界面允许单独关闭高耗时项目，但不允许在同一报告中给不同模型选择不同的公共测试条件。

模型上限通常只选一个；不选时沿用各模型一致的原配置。开启“多档上限测试”才允许至少两个上限档位，每档重复当前预设及已选项目，装不下的输入标记为档位不适用。普通模式多选会被拒绝，界面取消多档开关时自动保留从小到大的第一个档位并取消其他勾选。运行确认显示含缓存和并发重启的计划服务启动次数，以及性能、召回、并发与容量工作量。

### 4.3 运行控制

- 开始测试
- 安全停止
- 打开当前报告目录
- 打开已完成的 HTML 报告
- 当前轮次、当前模型、当前测试单元和完成进度
- 最近一条错误或状态信息

关闭进度窗口不应直接杀死未知进程。安全停止只结束本次 Benchmark 记录的 Python Server 和 `strata.exe` 进程树。

## 5. 测试内容

### 5.1 基础性能

默认 API 参数：

```json
{
  "temperature": 0,
  "reasoning_effort": "none",
  "max_tokens": 256,
  "stream": false,
  "cache_prompt": false,
  "chat_template_kwargs": {
    "enable_thinking": false
  }
}
```

每个模型每轮重新启动一次。服务就绪后执行不计分的预热，再执行正式测试。模型顺序按轮次反转，减少固定先后顺序造成的缓存和温度偏差。

正式记录：

- 模型加载耗时
- 实际 Prompt tokens
- 实际 Completion tokens
- Prompt tok/s
- Decode tok/s
- 引擎预填充耗时（来自 `prompt_ms`，不是客户端 TTFT）
- 请求总耗时
- MTP draft 数和接受数
- MTP 接受率
- RAM 峰值
- VRAM 峰值
- 进程退出、超时和 API 错误

Prompt 使用固定本地语料构造目标长度；先由当前模型 tokenizer 校准，再加入每次运行唯一 nonce，正式请求以服务返回的实际 token 数验证输入档位（±5%）。冷输入额外核对缓存复用数为零。请求还必须返回有效内容、正数输出 token 和 Prompt/Decode 速度指标，才计为有效性能样本。

### 5.2 对话缓存

使用当前模型 tokenizer 校准约 32K 的初始上下文，随后在同一会话中进行两轮追问。首轮真实输入需落在目标的 ±5% 内，公共前缀复用不得超过目标的 1%；两次追问各至少复用目标的 40%，缺少复用计数或有效输出记为失败。记录：

- 每轮 Prompt tokens
- 复用 tokens
- 新处理 tokens
- 引擎预填充耗时（来自 `prompt_ms`）
- Prompt 和 Decode tok/s
- 总延迟
- 内存变化

缓存测试和无缓存基础性能分开汇总，不混用速度结果。

### 5.3 Agent 能力

任务集使用 JSON 描述，测试类型包括：

- JSON Schema 输出
- Tool Call 名称与参数
- 多约束指令遵循
- 给定历史消息后的信息提取
- 给定工具错误消息后的下一次调用参数
- 固定小型代码修复的文本断言
- 长资料证据定位
- `reasoning_effort=none` 行为检查

本题集共 7/9 道，每题只请求一次模型并做确定性断言。给定的历史消息和工具错误是题面，测试器没有真正执行工具或连续 Agent 流程；代码题只检查返回的修正语句，没有执行代码。因此通过率只称为“内置题集通过率”，不代表通用智力或 Agent 总体能力。原始答案保留供人工查看；请求执行成功与断言通过分别记录。

Agent 主测试使用 `reasoning_effort=medium`、`temperature=0` 和固定 seed；关闭思考检查单独使用 `none`。

### 5.4 长上下文召回

调用项目内 `tools/needle_bench.py`。日常速测使用 4K；日常完整使用 4K/32K；长文对照使用 32K/128K；容量极限使用 256K。每种长度均测 10%、50%、90% 三个位置。Benchmark 调用工具时启用服务端 tokenizer 校准，并核验正式响应的真实输入长度在目标的 ±5% 内；校准失败或偏差过大均记失败。工具单独运行时保持原默认方式。请求失败和缺失样本保留在应测题数中，报告不会因此抬高召回率。长度超过当前临时配置能力时记录为档位不适用，不作为失败。

### 5.5 并发性能

调用项目内 `tools/serve_load.py`。日常预设只测 4K，并发专项测 4K/32K；每档组数随预设为 1、2 或 3。所选输入长度与预设并发长度取交集；未传入 `--context-lengths` 的 CLI 使用预设长度。并发提示词使用与性能测试相同的本地文档语料和目标输入档位，每条请求在语料前加入不同 nonce 与写作任务。每条请求最多生成 256 tokens。报告记录输入档位、服务返回的实测输入 token 范围、缓存复用 token 上限、输出时间重叠、总吞吐、单请求速度、客户端 TTFT P50/P95、总延迟 P50/P95 和错误数。缺失实测输入或缓存数据、输入与目标差距超过 10%、缓存复用不为零、或多客户端输出时间未重叠时标记失败。Benchmark 默认关闭并发阶段提示词缓存，并核对服务端实际 serving 槽数。

### 5.6 稳定性

完整测试连续发送 10 次同类短请求，每条有唯一标识；只有取得有效输出内容和正数输出 token 的请求才记成功。记录错误、超时、进程退出、速度变化和 RAM/VRAM 高水位。稳定性结果独立呈现，不与单次峰值速度合成一个分数。容量探测已发请求但证据不足时，阶段状态为部分完成，不写成未执行。

## 6. 执行流程

1. 验证所选模型配置和本地文件。
2. 检查目标 Benchmark 端口与日常 Strata 端口。
3. 如果发现日常 Strata 正在运行，阻止开始并提示先用启动器停止。
4. 创建带时间戳的报告目录。
5. 采集硬件、驱动、Strata Git/Engine 版本和当前系统状态。
6. 为每个模型创建只用于本次测试的配置副本。
7. 按轮次交错启动模型、预热、执行测试并停止。
8. 每完成一个请求立即追加原始记录，避免中途失败丢失全部结果。
9. 汇总成功、失败和跳过项目。
10. 生成 Markdown、JSON 和本地 HTML 报告。
11. 恢复启动器原来的模型选择；不自动重新启动日常 Strata 服务。

## 7. 进程和错误处理

编排器记录自己启动的根 Python PID、子进程和测试端口。停止时重新验证 PID、可执行文件路径、父子关系和端口身份，只结束匹配本次运行记录的进程树。

单个请求失败时：

- 写入失败记录
- 保存对应 Server 日志
- 按策略继续下一次重复或下一测试单元

单个模型无法启动时：

- 将该模型标记为启动失败
- 保存配置副本和启动日志
- 安全停止其残留进程
- 继续测试其他模型

磁盘空间不足、报告目录无法写入、Python 环境缺失或官方脚本缺失时，在启动任何模型前停止。

## 8. 输出结构

```text
launcher/reports/YYYY-MM-DD_HH-mm-ss_<preset>/
  report.html
  report.md
  summary.json
  raw-results.jsonl
  hardware.json
  run-manifest.json
  configs/
  prompts/
  answers/
  logs/
```

`run-manifest.json` 保存：

- 报告格式版本
- 测试开始和结束时间
- 所选模型和配置文件
- Strata 版本
- 测试预设和公共参数
- 每个测试阶段状态
- 用户中止状态

每条 `raw-results.jsonl` 记录必须包含模型名称、配置快照标识、轮次、测试类型、目标长度、实际 token 数、计时、内存指标和状态。

## 9. 报告原则

报告不产生一个掩盖差异的综合总分，分别展示：

- Prompt 处理速度
- Decode 速度
- TTFT 和总延迟
- 缓存复用表现
- Agent 任务通过率
- 长上下文召回率
- 并发性能
- 稳定性
- RAM/VRAM 占用

每个汇总数字可追溯到原始运行记录。统计至少提供样本数、中位数、最小值和最大值；并发测试提供 P50/P95。

### Markdown 分享摘要规范

`report.md` 是可复制的简明对照报告，不承担完整审计记录。正常跑测完成与 `render` 命令重新生成报告时，都必须通过 `render_reports()` 调用同一个 Markdown 生成逻辑。修改模板后，新运行自动采用新格式；历史报告只有明确重新生成时才更新。

- 第一段为“**一句话分享**”，不超过 180 个字符，复制后可直接发评论。优先使用所有入选模型都有有效样本的同一性能输入档，注明 Decode 中位数、单位和各模型样本数；其次可使用有效的双客户端总吞吐、容量召回或内置题集断言结果。没有可比较数据时明确写“无可比较的有效结果”，运行未完整完成时标明部分完成。不得把配置上限写成实测输入长度，也不得把 Agent 题集结果称作总体智力。
- 正文仅生成本次实际选中项目的表格，保留模型/上下文档位、输入档和实测 token、样本数、关键速度或通过数、并发槽数及输出重叠、必要的环境与异常状态。未选项目不出现空表；未勾选容量探测时不出现容量通过结论。
- 表格中的性能预填充使用引擎 `prompt_ms`，并发 TTFT 使用客户端计时，二者标签不得混用。内存采样注明约 1 秒间隔；失败或未执行不得显示成有效速度或 `0/0` 通过率。
- 配置快照、所有逐请求字段、原始回答、完整内存阶段表及详细错误留在 `report.html`、`summary.json`、`raw-results.jsonl` 与报告目录其他文件中，Markdown 只给这些文件的链接。所有摘要数字仍可追溯到原始记录。

## 10. 安全与更新兼容性

- Server 只监听 `127.0.0.1`。
- Benchmark 不下载模型、依赖或更新。
- 不写入官方设置文件。
- 不修改或覆盖模型 JSON。
- 不结束未被本次运行记录并重新验证的进程。
- 报告不保存 API key。
- 自定义实现限制在未跟踪的 `launcher/` 目录，官方更新通常不会触碰它。
- 如果未来官方增加同名 `launcher/` 路径，更新前检测路径冲突并提示迁移。

## 11. 验收标准

实现完成需满足：

1. 能选择至少两个模型并自动顺序完成基础性能测试。
2. 原始模型 JSON 和官方设置文件在测试前后字节不变。
3. 每次运行生成独立报告目录和配置快照。
4. 中途终止后保留已完成结果且没有残留测试进程。
5. 单个模型启动失败不会丢失其他模型结果。
6. HTML、Markdown 和 JSON 汇总中的数字能追溯到 `raw-results.jsonl`。
7. 报告明确区分模型、轮次、冷启动、预热和正式结果。
8. 官方 `needle_bench.py` 和 `serve_load.py` 的结果被纳入统一报告。
9. 日常启动、停止、保存、校准和官方工具入口保持可用。
10. 官方跟踪文件无修改。
